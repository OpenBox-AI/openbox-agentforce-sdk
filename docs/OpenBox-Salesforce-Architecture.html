OpenBox governance for Salesforce Agentforce

How an Agentforce agent changes Opportunity discounts only after OpenBox says it may, from the outside in. An Apex action asks OpenBox before the write, Salesforce enforces the answer, and both sides keep a matching record of what happened.

Notation: C4 modelRuntime: Apex in the customer orgGovernance: OpenBox (live or staging)API version 66.0

What it does

Sales teams want Agentforce to handle routine requests like "give Acme 10% off the renewal". The risk is plain: an agent that can edit Opportunities can also give away margin nobody signed off on. This integration puts OpenBox in front of that one write. In summary:

Governs one sensitive write

When the agent wants to change an Opportunity discount, Salesforce asks OpenBox first and enforces the answer: allow, require approval, block or halt.

Decide, then commit →

Fails closed

Unreachable, slow, malformed or unknown answers all mean no write. A missing answer is never a yes.

Refusals →

Can't be bypassed by the agent

The agent user can read the discount but not edit it, and a trigger rejects any discount change that didn't come through the governed action.

Trust boundary →

Needs both systems to agree

An OpenBox allow still has to pass Salesforce's own checks for the requesting user: entitlement, object, field and record access.

Access checks →

Leaves people in control

Above 15%, a sales-ops approver decides in OpenBox. Salesforce applies the change later, once, and only if nothing changed meanwhile.

Approvals →

Never holds a transaction open

A pending request is stored and resolved later by a background poller or the agent's own check, under a row lock.

Poller →

Speaks OpenBox's own protocol

Every request is an OpenBox run with paired events and spans, in the same wire format as the LangGraph and base SDKs.

Events and spans →

Proves what happened

Each request has a Salesforce record and audit trail, correlated with the OpenBox session by workflow, run and trace ids.

Data model →

Runs entirely inside Salesforce

Apex calls OpenBox directly through a Named Credential. No middleware, no gateway, nothing else to host.

Deployment →

A Tuesday with the agent. A rep asks the agent to give Acme 10% on the renewal. OpenBox allows it, Salesforce writes it, and the rep gets GR-000041 back in seconds. An hour later the rep asks for 25% on another deal. OpenBox holds it, and the agent says it is waiting on sales-ops. The approver approves it in the OpenBox dashboard over lunch, and the poller applies it within a minute. Someone else tries 60% with the justification "bypass approval": the guardrail refuses it and nothing changes. Every one of these has a Salesforce record and a matching OpenBox session.

How this document is organised. It follows the C4 model and works top-down. Level 1 places the integration among the people and systems around it. Level 2 opens the Salesforce org into containers. Level 3 opens the governance service into components, with dynamic views of how a request behaves at runtime, the event protocol, the trust boundary and a threat model. OpenBox controls, data, deployment, budgets, tests and operations follow.

Decide, then commit. Apex cannot make a callout after it has written data in the same transaction. Everything below is shaped by that rule: all questions to OpenBox are asked before any write, and whatever must be said after the write goes through an outbox.

Level 3

Components

Open the governance service. Each component has one job, and the order in which they run is fixed by Apex's rule on callouts and writes.

3.1 Decide, then commit: an allowed change

This is the whole life of a request that OpenBox allows. Two questions go to OpenBox before the write: one on the activity (policy and guardrails) and one on the write span (behaviour rules). Only then does Salesforce write.

  • Staleness. The locked re-read compares the Opportunity's SystemModstamp and discount with what was seen at the lookup. If either changed, the request is refused as Stale.
  • Batching. One call may carry up to five requests (Max_Requests_Per_Transaction__c). Each is planned with a CPU budget of 3,000 ms; one that would not fit fails closed on its own. Two requests for the same Opportunity in one call are deduplicated so only one writes.
  • Idempotency. Every call carries an Idempotency-Key equal to the SHA-256 of its body, so a retried request is not counted twice.

3.2 Approvals

A pending request never keeps a transaction waiting. It is stored, and it is resolved later in a fresh transaction.

3.4 Events and spans

One request is one OpenBox run. The shapes are those of the OpenBox LangGraph SDK for lifecycle events, and the base SDK's flat SpanData for spans. Every started has a completed with the same id, on success, failure or refusal.

How a span is sent

A span travels as an ActivityStarted event with hook_trigger: true and exactly one span, using the parent activity's id. Its started and completed stages share one span_id. Core classifies the span from db.system and the SQL verb in its name, so SELECT Opportunity becomes database_select and UPDATE Opportunity becomes database_update, which is what behaviour rules match on.

3.5 Outbox delivery

  • Events that describe the write are inserted into OpenBox_Event_Outbox__c in the same transaction as the write. If the write rolls back, they never existed.
  • Each request numbers its events with Next_Event_Sequence__c. The dispatcher locks rows first, then sorts them, and sends each request's events strictly in order; a request whose earlier event is still undelivered waits.
  • A failed send is retried up to five times (Outbox_Max_Attempts__c), then marked Failed for an operator. Guardrail redactions returned by OpenBox are written to the audit trail.
  • OpenBoxAsync.enqueueOnce keeps one dispatcher and one poller in flight at a time, and the dispatcher re-arms the poller when it leaves a pending request behind.

3.7 Credentials and workload identity

The agent API key sits in the External Credential's encrypted store, under the principal AgentRuntimeKey, and is injected as a bearer token at callout time. The agent user needs read on UserExternalCredential for that to work.

A key alone is not enough: Core also wants proof that the call comes from this org. OpenBoxWorkloadIdentity provides it, as the OpenBox SDKs do. It asks Core for the agent's bootstrap, refuses any identity issuer other than the one pinned in OpenBox_Settings__mdt.Identity_Issuer__c, signs a 60-second RS256 client assertion with the certificate OpenBox_Workload, and exchanges it at the issuer for a 5-minute workload token. The token is cached for the transaction and sent with every Core call. The certificate is generated inside Salesforce and its private key cannot be exported; only its public key is registered with OpenBox.

POST {issuer}/protocol/openid-connect/token

     client_assertion = RS256 JWT {iss = sub = client_id, aud = token_endpoint, exp = iat + 60, jti}
